# Homelab DevOps Engineer

Домашняя лаборатория из 5 виртуальных машин. Настраивал всё руками, без Ansible, чтобы разобраться как это работает под капотом.

Есть вторая часть этого проекта, где та же инфраструктура автоматизирована через Ansible: https://github.com/al-kv/ansible-homelab-project

![Схема сети](network-scheme.png)

## Что настроено

5 виртуалок на VirtualBox (Bridged Adapter):

1. **vm-ctrl** (192.168.1.131, admin). Управляющая машина, на ней лежат скрипты и cron.
2. **vm-web** (192.168.1.82, admin). Nginx с двумя сайтами и реверс-прокси на Python (порт 9000).
3. **vm-dns** (192.168.1.94, admin). Pi-hole как основной DNS и блокировщик рекламы.
4. **vm-vpn** (192.168.1.77, admin1). WireGuard сервер с NAT и маршрутизацией.
5. **vm-legacy** (192.168.1.62, student). Rocky Linux с SELinux в режиме Enforcing и firewalld.

Все машины в подсети 192.168.1.0/24, шлюз 192.168.1.1. DNS раздается через Pi-hole. На Ubuntu/Debian стоит ufw, на Rocky firewalld. SSH работает только по ключам ed25519, пароли и вход под root отключены.

## Секреты

**SSH-ключи.** Приватный ключ лежит только на vm-ctrl, никуда не копируется. Публичный ключ добавлен в authorized_keys на остальные 4 машины. Права на файлы строго 700 для папки .ssh и 600 для самих ключей, иначе SSH откажется работать.

**WireGuard.** Приватный ключ сервера лежит только на vm-vpn, приватный ключ клиента только на Windows. В конфигах только публичные ключи друг друга. В папке configs лежат шаблоны конфигов с замазанными ключами (REDACTED) исключительно для примера.

**Sudoers.** Скрипты на vm-ctrl заходят на другие машины по SSH и используют sudo. Чтобы автоматизация не падала с ошибкой "a terminal is required", настроен NOPASSWD. Но не ALL, как часто делают в спешке, а только для конкретных команд, которые реально нужны скриптам:

- vm-ctrl, vm-web, vm-dns (admin): systemctl, tar, tee, du, ufw, mkdir, rm, lynis
- vm-vpn (admin1): systemctl, wg, du, ufw, rm
- vm-legacy (student): systemctl, lynis, firewall-cmd, du, rm

**Pi-hole.** Пароль от веб-интерфейса лежит в /etc/pihole/pihole.toml, доступен только root.

## 18 проблем с которыми я столкнулся

**1. VirtualBox ругается на Image checksum error.** При создании VM была включена галочка Unattended Installation. VirtualBox подсовывал свой viso файл вместо реального ISO. Решается удалением этих файлов и ручным подключением ISO через настройки носителей. На Rocky и Fedora эту галочку лучше сразу отключать.

**2. sudo: unable to resolve host.** В /etc/hosts не было записи с именем хоста. Нужно добавить строку 127.0.1.1 vm-ctrl, иначе sudo не может залогировать действие.

**3. netplan: malformed address.** Опечатка в IP адресе, пропустил последний октет. Netplan не прощает ошибок в YAML, пришлось переписать заново.

**4. ufw enable прервался с Aborted.** На вопрос "Command may disrupt existing ssh connections" я ввел не y, а другую команду. Ответить нужно строго y и Enter. Если правило для 22/tcp уже добавлено, SSH не оборвется.

**5. Pi-hole отвечает REFUSED на все запросы.** При установке не прописал upstream DNS. Pi-hole принимал запросы, но не знал куда их передавать. Решается командой pihole-FTL --config dns.upstreams '["1.1.1.1"]' и перезапуском сервиса.

**6. Debian не видит соединение enp0s3 в nmcli.** На Debian NetworkManager называет соединение "Wired connection 1", причем с пробелами. Сначала нужно посмотреть реальное имя через nmcli connection show, а потом уже менять настройки.

**7. SSH пишет Server refused our key.** Файл authorized_keys принадлежал root, а не пользователю. SSH игнорирует файлы, у которых неправильный владелец или слишком широкие права. Помогает chown -R user:user ~/.ssh и chmod 700/600.

**8. Host key verification failed.** SSH не знал ключ целевой машины. Для скриптов идеально использовать флаг -o StrictHostKeyChecking=accept-new, он принимает новые хосты, но предупреждает если ключ вдруг изменился.

**9. sudo: a terminal is required.** В SSH-сессии нет TTY, а sudo по умолчанию требует пароль через терминал. Решается настройкой NOPASSWD в sudoers (см. раздел Секреты).

**10. WireGuard: handshake did not complete.** В клиентском конфиге в AllowedIPs была указана локальная сеть 192.168.1.0/24. Маршрут создавался через туннель, и запрос до самого сервера пытался уйти в этот же туннель, которого еще нет. Петля. Убрал локальную сеть из клиентского конфига.

**11. WireGuard рвет SSH при рестарте.** В серверном конфиге в AllowedIPs была указана локальная сеть. wg-quick создавал маршрут, и весь трафик к домашней сети уходил в туннель. Нужно оставить в AllowedIPs только VPN-адрес клиента (10.10.0.2/32).

**12. После старта WireGuard упал пинг до соседних машин.** Правило iptables MASQUERADE было без указания источника. Маскарадился весь трафик, включая локальный. Добавил -s 10.10.0.0/24.

**13. iptables -F POSTROUTING оборвал SSH.** Сброс таблицы NAT убил состояние существующих TCP-сессий. Такие команды нужно делать только из консоли VirtualBox, а не по SSH.

**14. chmod: Operation not permitted.** Файлы скриптов были созданы через sudo vi, владелец root. Вернул владельца через chown и только потом сделал chmod +x.

**15. cron не пишет логи в /var/log.** Cron запускает задачи от обычного пользователя, а в /var/log может писать только root. Логи скриптов теперь пишутся в /home/admin/logs, а отчеты скриптов - в специально созданные папки с правильными владельцами.

**16. lynis: command -v пусто через sudo.** command это встроенная команда bash (builtin), а sudo не умеет их вызывать. Пришлось обернуть в sh -c.

**17. lynis на Rocky создает пустой отчет.** Флаг --quiet в новых версиях подавляет вообще весь вывод. Заменил на --no-colors.

**18. lynis падает с Warning: PID file exists.** После Ctrl+C остается PID файл, и следующий запуск думает что процесс уже идет. В скрипте security_audit.sh перед запуском добавлено превентивное удаление /var/run/lynis.pid.

## Скрипты и cron

Все скрипты лежат на vm-ctrl в /home/admin/scripts и добавлены в cron.

**check_services.sh** проверяет nginx, pyserver, pihole-FTL, wg-quick и nginx на всех машинах. Запуск каждые 15 минут. Если сервис упал или хост недоступен, пишет в syslog через logger. Умеет отличать недоступный хост от упавшего сервиса.

**backup_nginx.sh** забирает /etc/nginx с vm-web по SSH, проверяет архив на целостность и размер. Если архив битый или слишком маленький, удаляет его и завершается с ошибкой. Хранит 7 последних бэкапов в /var/backups/nginx/.

**disk_report.sh** собирает df -h и du -sh /var/log со всех машин. Пишет в /var/log/homelab/disk_report.log.

**security_audit.sh** запускает lynis audit system на всех машинах по воскресеньям. Понимает что код возврата 1 или 2 у lynis это норма (найдены замечания), а не ошибка выполнения.

Расписание в crontab:

    */15 * * * * /home/admin/scripts/check_services.sh  >> /home/admin/logs/check_services.log 2>&1
    0    * * * * /home/admin/scripts/disk_report.sh     >> /home/admin/logs/disk_report.cron.log 2>&1
    0    3 * * * /home/admin/scripts/backup_nginx.sh    >> /home/admin/logs/backup_nginx.log 2>&1
    0    4 * * 0 /home/admin/scripts/security_audit.sh >> /home/admin/logs/security_audit.log 2>&1

## SELinux на Rocky

SELinux был в режиме Enforcing. Nginx запускался, но отдавал 403. По умолчанию SELinux запрещает процессу httpd_t инициировать сетевые соединения. Так как у меня Nginx работает как реверс-прокси, ему нужно ходить на 127.0.0.1:9000. Разрешил командой sudo setsebool -P httpd_can_network_connect on. Флаг -P сохраняет настройку после перезагрузки.

## Проверка VPN

С Windows клиента пинг до vm-dns (192.168.1.94) проходит без потерь. Пинг до самого шлюза 10.10.0.1 не идет, потому что Windows firewall блокирует ICMP-ответы, но на маршрутизацию трафика в локальную сеть это никак не влияет.

Вывод wg show на сервере:

    interface: wg0
      listening port: 51820
    peer: <CLIENT_PUBLIC_KEY>
      allowed ips: 10.10.0.2/32

## Как развернуть у себя

Это не готовый инсталлятор, а документация моего проекта. Если хотите повторить:

1. Поднять 5 VM, настроить статические IP.
2. Поменять IP и имена пользователей в скриптах и конфигах на свои.
3. Настроить SSH-ключи между машинами.
4. Скопировать конфиги из папки configs на нужные машины и применить их.
5. Заполнить свои ключи в конфигах WireGuard.
6. Прописать cron задачи.
7. Запустить check_services.sh и убедиться что все сервисы в статусе [OK].
